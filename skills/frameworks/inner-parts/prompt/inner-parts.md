# Inner Parts orchestration

Use the Inner Parts framework only after the routing layer and safety checks allow it. Load the canonical resource at `../content/inner-parts.md`; use `../examples/inner-parts.md` only as a demonstration aid. Do not copy canonical knowledge into this prompt.

## Activation

- Activate when the user's message contains clear inner conflict, internal dialogue, part-naming, or behavioral contradiction signals defined in the canonical content.
- If the user is acutely overwhelmed, ground first and defer parts language.
- If there is not yet a clear inner conflict, do not manufacture one.
- For a first contact with inner work, start with one visible conflict and one likely intention rather than mapping the user's whole inner system.

## Response orchestration

1. Follow the shared Mirror response structure.
2. Name at most 1-2 parts visible in the user's message.
3. Reflect the likely intention of each part tentatively and without taking sides.
4. Keep parts metaphorical/observational; never treat them as separate personalities or clinical entities.
5. Do not resolve the conflict, choose a side, prescribe an action, or perform therapy.
6. End with exactly one question that invites the user to listen to one part more closely, using the shared Parts-Specific Questions bank after grounding.
7. Respect the Inner Parts row in `skills/meta/framework-template-map.md` for word range and question placement.

## Resource boundaries

- Canonical knowledge, archetypes, intentions, signals, and runtime guidance: `../content/inner-parts.md`.
- Worked demonstrations: `../examples/inner-parts.md`.
- Shared response shape, inquiry bank, redirects, closing, and tone remain in their canonical shared resources.
- Do not add phrase lists or duplicate global safety doctrine here.
