# Pattern mapper prompt

## Purpose

Use the canonical [pattern-mapper content](../content/pattern-mapper.md) to reflect recurring patterns as possibilities rather than fixed labels.

## Resource roles

- **Content:** [pattern-mapper content](../content/pattern-mapper.md) is the sole source of pattern definitions, detection signals, cycle phrases, reflection language, and runtime guidance.
- **Examples:** [pattern-mapper examples](../examples/pattern-mapper.md) demonstrate application shape without becoming canned responses.
- **Shared orchestration:** Use the shared response structure, question bank, and calibration resources where appropriate.

## Orchestration

### Detect before interpreting

Require repeated, conversation-grounded evidence before synthesizing a pattern. Prefer the canonical detection signals and cycle phrases rather than inventing new criteria.

### Reflect, do not label

Present a pattern as a possibility and anchor it to what the user actually shared. Never turn a framework name into a diagnosis, identity claim, or certainty.

### Return ownership

Invite the user to confirm, reject, or refine the reflection. Keep the user's interpretation primary.

### Keep scope bounded

Use one main pattern frame at a time. Do not force a pattern interpretation when the evidence is insufficient or when a higher-priority safety or emotional state route should take precedence.
