How it works

Architecture

SoulMap's routing is deterministic. No model decides which framework applies. A message is scored against phrase lists authored in Markdown, routed by a priority order written in doctrine, and the resulting response is validated before it reaches the reader.

The request path

  1. Message and historyWhat the person wrote, plus the conversation so far.
  2. Safety detectionCrisis and dependency are checked first, as protected modules separate from ordinary framework routing.
  3. Framework selectionDetectors score the message against phrases owned by Markdown knowledge files. The highest-priority match wins. Exactly one primary framework is selected.
  4. Knowledge lookupThe selected framework's Markdown file supplies the reflective guidance and response shape.
  5. Response safety gateThe gate re-derives crisis and dependency status independently, so a routing miss cannot silently produce an unsafe response.
  6. Response contract validationGenerated wording is checked for diagnosis, prediction stated as fact, dependency reinforcement, guru positioning, and loss of user independence.
  7. ResponseOne framework, one question at most, and that question last.

Markdown owns the knowledge

Reflective content lives in Markdown, not in code. Python loads phrase lists and guidance from those files rather than hardcoding them, so the knowledge stays reviewable by people who do not read Python.

Python owns enforcement only

The runtime routes, detects, and validates. It does not generate response wording. That boundary is deliberate and documented as an architectural limit rather than a gap to close later.

What this site does not do

This website explains the architecture. It does not run it. There is no API here, no session, and no reflective interface. SoulMap belongs inside a conversation a person has chosen to have, not inside a page visit.
