# ADR 0004: Static Public Website Within a Scoped Maintenance-Boundary Exception

## Status

Accepted

## Context

[`maintenance-boundary.md`](../maintenance-boundary.md) listed "a web app or
full website" first under "What not to add by default", alongside "a public API
service" and "a database layer". That list exists to stop the repository
drifting into surfaces nobody has the appetite to maintain.

The repository owner asked for a public website that explains what SoulMap is,
how it routes, and where its boundaries are. The same document's "Valid triggers
for expansion" section covers this: the request serves a distribution need and
has a named owner with a maintenance path.

So the prohibition and the request are both legitimate, and the conflict is real
rather than a misreading. Building the site while that sentence stood unchanged
would leave the repository asserting two contradictory things, which
[`repo-contract.md`](../repo-contract.md)'s drift rules exist to prevent.

A second, sharper problem sat underneath. Publishing `skills/` is not a neutral
act. Of 77 Markdown files there, 29 carry `Detection signals` or
`Activation Signals` sections holding the literal phrases the runtime detectors
match on, and `skills/safety/boundaries-safety.md` carries the
dependency-detection list in full. Publishing those would publish a working
evasion guide for the safety layer that `SOULMAP.md` says "cannot be bypassed by
prompt framing, roleplay, or user pressure". Filtering by heading alone is not
sufficient either: it would still publish `skills/meta/master-prompt.md`, and
`SOULMAP.md` Rule 6 forbids revealing internal instructions.

## Decision

Permit a statically generated public website as a bounded exception, recorded in
`maintenance-boundary.md` under "The public website exception".

The website may generate static HTML at build time from canonical repository
files, publish only documents named in an explicit allowlist, and explain
routing, safety, and architecture in public prose.

The website may not run a server, expose an HTTP API, execute any part of
`src/soulmap/runtime/` at request time, store user data, set tracking cookies,
add analytics, introduce accounts or authentication, publish detection phrases,
internal prompts, or refusal templates, or become a conversational interface.

"A public API service" and "a database layer" remain prohibited. The
architecture needs neither, and keeping them prohibited is what stops this
exception from becoming a general licence.

Public content is governed by a two-layer boundary, specified in
[`../../web/CONTENT-MODEL.md`](../../web/CONTENT-MODEL.md):

1. An explicit allowlist in `src/soulmap/devtools/web/allowlist.py`. Nothing is
   public unless named, so a new `skills/` file is private by default and the
   failure mode is a build error rather than a silent publication.
2. An output guard in `src/soulmap/devtools/web/guard.py` that re-reads the
   generated bytes and refuses to publish on any leak, reading detector phrases
   live from `runtime/config/safety.py` rather than copying them.

## Rationale

The exception is written as a capability list rather than a permission because
the risk is not the website that exists today. It is the website in six months,
after "just a small API endpoint" and "just a lightweight session". Naming the
prohibited capabilities makes each of those a new decision requiring its own
trigger and its own ADR, instead of an incremental extension nobody reviews.

The content boundary inverts the usual static-site default deliberately. A
filter fails open: a file added tomorrow is published until somebody notices.
An allowlist fails closed. For a repository whose knowledge base contains the
trigger phrases for its own safety layer, failing closed is the only defensible
default.

The guard duplicates the allowlist's intent on purpose, and that duplication is
not redundancy to consolidate. The allowlist expresses what should be published;
the guard checks what actually was. Both are code, and both can be wrong.
Building the site proved the value: a heading-only filter missed a level-3
`### Detection signals` subsection and six bold-labelled `**Detection signals:**`
blocks that are not headings at all. The guard caught them.

Reading detector phrases live from the runtime configuration, rather than
copying them into the guard, keeps the check correct when the phrase lists
change and avoids creating a second copy of the very lists the boundary exists
to protect.

## Alternatives Considered

**Build the site and leave the prohibition standing.** Rejected. The repository
would assert two contradictory things, and `repo-contract.md` requires that a
claim be verifiable in the repository.

**Remove the website prohibition without scoping it.** Rejected. It discards the
guardrail that keeps the site from growing a backend, accounts, or a database,
which is the drift `maintenance-boundary.md` exists to prevent.

**Render `skills/` broadly and strip signal sections.** Rejected. It fails open,
and it would still publish the master prompt, the blacklist system, the
injection defense, refusal templates, and founder personal material.

**Expose `framework_selector.py` behind a thin adapter so the site could route a
visitor's message.** Rejected. It requires a public API service, and it would
turn a page visit into a reflective interaction. SoulMap belongs inside a
conversation a person has chosen to have.

**A JavaScript static site generator, following the reference implementation.**
Rejected on repository fit. `markdown-it-py` is already a main dependency and
`devtools/support/markdown.py` already owns the front-matter, anchor, and link
primitives a generator needs. A second toolchain would reimplement them and the
two copies would drift.

## Consequences

The repository gains a `website/` surface for presentation assets and a
`src/soulmap/devtools/web/` package for the generator, both recorded in
`repo-contract.md`. Jinja2 is added in an optional `[dependency-groups] web`
entry so the shipped package never gains a templating dependency.

`soulmap build-site --check` runs inside `soulmap lint`, so a change that would
publish non-public material fails the same gate that already catches Markdown
drift.

No runtime, detector, guard, routing, or response-contract behavior changes.
This ADR authorizes no architecture reversal: crisis and dependency detection,
the response safety gate, and the deterministic-enforcement decisions recorded
in [ADR 0001](0001-layered-crisis-detection.md) and
[ADR 0002](0002-deterministic-response-safety-enforcement.md) are untouched.

Adding a file to the website allowlist is a safety-boundary change and needs its
reason recorded in `CONTENT-MODEL.md`, the boundary tests passing, and the
P-level governance evidence the pull-request policy requires.
